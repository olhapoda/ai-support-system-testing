# Бенчмарк LLM-моделей на розпізнаванні кризових повідомлень

Готовий каркас для дослідження №3: порівняння кількох LLM API за
точністю класифікації, затримкою та вартістю запиту на наборі з 18
тестових фраз (6 нейтральних, 6 зі стрес-маркерами, 6 із кризовими
маркерами).

**Важливо про самі фрази**: вони навмисно абстрактні й узагальнені —
без конкретних методів, планів чи деталей, лише загальні маркери на
кшталт тих, що використовують клінічні опитувальники-скринінги. Це
свідомий вибір, синтетичні дані, не реальні повідомлення користувачів.

## Крок 1. Отримай API-ключі

Тобі знадобляться ключі від тих провайдерів, яких хочеш порівняти
(можна лишити 2 з 3, якщо не всі потрібні):

- **OpenAI** — platform.openai.com → API keys
- **Anthropic** — console.anthropic.com → API keys
- **Google Gemini** — aistudio.google.com → Get API key

⚠️ Ці виклики платні (хоч і копійчані для 18 фраз). Перевір баланс і
ліміти на своєму акаунті перед запуском.

## Крок 2. Перевір актуальність назв моделей і цін

У файлі `benchmark.js` я вписала назви моделей і ціни за 1 мільйон
токенів, **актуальні на момент написання цього коду**. Оскільки
провайдери регулярно оновлюють лінійку моделей і тарифи, перед
запуском:

1. Зайди в документацію кожного провайдера (розділ "Models" /
   "Pricing").
2. Звір або онови рядки `PROVIDERS` у `benchmark.js` — особливо поле
   `call: (t) => call...('назва-моделі', t)` та `priceIn` / `priceOut`.

Це найважливіший крок — застарілі ціни чи неіснуюча назва моделі
означають, що вартість запиту в результатах буде неправильна.

## Крок 3. Встанови залежності й налаштуй ключі

```
npm install
cp .env.example .env
```

Відкрий `.env` і встав свої ключі:

```
OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=sk-ant-...
GEMINI_API_KEY=AI...
```

Якщо тестуєш не всі три провайдери — просто видали відповідний рядок
з масиву `PROVIDERS` у `benchmark.js`.

 



## Крок 4. Запусти бенчмарк

```
npm run benchmark
```

У терміналі побачиш прогрес по кожній фразі й моделі в реальному
часі:

```
=== claude-haiku-4.5 ===
  #1 (neutral) → neutral [412 мс]
  #2 (neutral) → neutral [389 мс]
  ...
```

Результат також збережеться у файл `results.csv` — сирі дані на
випадок, якщо захочеш порахувати щось додаткове вручну чи в Excel.

## Крок 5. Порахуй метрики

```
npm run analyze
```

Це виведе таблицю: точність, середню затримку, середню вартість
запиту по кожній моделі — і окремо виділить, чи модель пропустила
якісь кризові сигнали (це найважливіша метрика для твоєї статті,
навіть важливіша за загальну точність).

## Крок 6. Що саме йде у статтю

- Таблиця з `analyze.js` (точність / затримка / вартість) — це і є
  твій "розрахунок" з вимог до статті.
- Окремо зверни увагу в тексті на випадки пропущених кризових
  сигналів (false negatives) — це найцінніший якісний результат:
  навіть одна пропущена модель серед трьох — сильний аргумент на
  користь того, чому потрібен окремий детермінований шар
  перестороги, а не покладання лише на LLM.
- У розділі "Обговорення результатів" чесно зазнач межу застосування:
  вибірка з 18 фраз замала для статистичної значущості — це пілотне
  порівняння, а не повноцінна валідація, і це нормально для статті
  такого обсягу.

## Якщо щось пішло не так

- **"Error: OPENAI_API_KEY is not defined"** — перевір, що файл
  називається саме `.env` (не `.env.example`), і що ключ вставлено
  без лапок.
- **Модель повертає щось інше, а не одне слово з трьох** — це теж
  цінний результат (одна з категорій відмов, яку ми обговорювали:
  "порушення формату відповіді"). Можеш зафіксувати в `results.csv`
  як окрему категорію помилки замість "неправильної класифікації".
- **429 / rate limit помилки** — збільш паузу між запитами в
  `benchmark.js` (зараз 300 мс, постав 1000).
