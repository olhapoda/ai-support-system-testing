# Тестування Firestore Security Rules

Готовий код для дослідження №2: емпірична перевірка правил доступу до
даних (`users/{uid}`, `conversations/{uid}/messages`) засобами
автоматизованого тестування у Firebase Emulator.

## Що тут є

- `firestore.rules` — самі правила безпеки
- `firebase.json` — конфігурація емулятора
- `test/firestore.rules.test.js` — 16 тестових сценаріїв
- `package.json` — залежності та команда запуску

## Крок 1. Перевір передумови

Тобі знадобляться:

1. **Node.js** версії 18 або новішої. Перевір командою:
   ```
   node -v
   ```
   Якщо не встановлено — завантаж з nodejs.org.

2. **Firebase CLI** (глобально):
   ```
   npm install -g firebase-tools
   ```
   Перевір встановлення:
   ```
   firebase --version
   ```

Логін у Firebase (`firebase login`) **не потрібен** — проєкт
називається `demo-psy-support-app` (префікс `demo-` каже Firebase CLI,
що це суто локальний емулятор без підключення до реального хмарного
проєкту).

## Крок 2. Розпакуй і встанови залежності

Розпакуй архів у будь-яку теку, відкрий термінал саме в цій теці і
виконай:

```
npm install
```

Це встановить `@firebase/rules-unit-testing` та `mocha`.

## Крок 3. Запусти тести

```
npm test
```

Що відбувається під капотом: ця команда сама піднімає емулятор
Firestore, чекає, поки він стане готовим, запускає всі 16 тестів і
після завершення сама ж емулятор вимикає — тобі не треба нічого
запускати вручну окремими командами.

**Важливо про перший запуск**: якщо це перший раз, коли на цьому
комп'ютері використовується емулятор Firestore, Firebase CLI сам
завантажить потрібний бінарник (~50-70 МБ) із серверів Google. Це
потребує інтернет-з'єднання і може зайняти хвилину-дві. Наступні
запуски будуть швидкими.

## Крок 5. Виміряй середній час обробки запиту (для статті)

```
npm run test:timing
npm run analyze:timing
```

Перша команда те саме, що `npm test`, але зберігає результат у
машинозчитуваному вигляді (`timing-results.json`) замість кольорового
виводу в термінал. Друга — рахує середнє, медіану, мінімум і максимум
по всіх 20 тестах, а також окремо — без першого тесту.

Чому окремо без першого: перший тест у прогоні майже завжди помітно
повільніший (у нас був 1912 мс проти 60-160 мс в решти) — це час на
встановлення з'єднання з емулятором, а не типова затримка обробки
запиту. Для статті коректніше наводити середнє "без холодного старту"
з відповідною приміткою, а не змішувати одноразові витрати з'єднання
із типовою продуктивністю.

## Крок 6. Збери результат для статті

У терміналі побачиш звіт mocha — щось на кшталт:

```
  users/{userId}
    ✓ 1. власник читає свій документ — дозволено
    ✓ 2. неавтентифікований користувач читає документ — заблоковано
    ...

  20 passing (Xs)
```

Саме рядок `20 passing (Xs)` (або, якщо щось не пройшло —
`19 passing, 1 failing`) і є тим емпіричним результатом, який іде в
розділ "Виклад основного матеріалу": скріншот або перенесений у
таблицю список сценаріїв з позначкою пройдено/не пройдено, плюс
статистика часу з кроку 5.

**Про написи "PERMISSION_DENIED" і "GrpcConnection ... error" в
консолі** — це нормально й очікувано. Коли тест перевіряє, що дія
має бути заблокована, він справді виконує цю дію і чекає відмови від
сервера; Firestore SDK виводить цю відмову як помилку з'єднання на
низькому рівні. Це не збій тесту — навпаки, це доказ, що правило
спрацювало. Орієнтуйся на підсумковий рядок `N passing`, а не на ці
проміжні написи.

## Якщо щось пішло не так

- **"Error: Cannot find module '@firebase/rules-unit-testing'"** —
  забула `npm install`, виконай крок 2.
- **"port 8080 is not open"** — щось інше вже займає порт 8080
  (можливо, залишився запущений емулятор з минулого разу). Зупини
  його або зміни порт у `firebase.json`.
- **Тест "падає" не там, де очікувалось** — це нормальний і цінний
  результат! Значить, або тест написано неточно, або правило потребує
  корекції. Обидва варіанти варто описати в розділі "Обговорення
  отриманих результатів" — це показує глибину аналізу, а не помилку.

## Що можна розширити (за наявності часу)

- Додати тестовий сценарій на дуже великий payload (перевірка
  обмежень розміру документа).
- Виміряти час виконання кожного тесту окремо (mocha виводить це у
  дужках після кожного `✓`) і навести середній час обробки запиту в
  статті.
